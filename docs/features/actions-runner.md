# Actions runner

An analysis runner for repos that carry the pollux-agent workflow. The server never calls an LLM for these repos; the repo's own Actions run Claude Code with the repo's credential. Setup: [Using the Actions runner](../guides/actions-runner.md). The same workflow writes a repo's first `docs/` when dispatched with PR number 0; see [Docs scaffold](scaffold.md).

## Flow

1. A push to a PR reaches the gate. The server computes the candidate docs (those whose `covers` at the merge base, the base-branch commit the PR's diff starts from, match a changed file) and the uncovered files (changed files no doc covers, not removed, not under `docs/`), and dispatches the workflow on the **default branch**, passing the head SHA, PR number, a fresh nonce, and the review input in the single `docs` input, a JSON object with `review`, `uncovered`, `base_sha` (the merge base), and `files` (every changed file with its commentable head-side line ranges); the server decides this input once, the same one the server runner renders into its prompts (the action still accepts a bare array or an object without `base_sha` and `files`). With no candidate and no uncovered file nothing is dispatched and the check concludes "No doc impact". The prompt tells the agent to review the candidates and to decide whether the uncovered files need a new doc. Dispatching the default branch's copy means a PR cannot change the workflow, its tools, or its secrets.
2. Before dispatching, the gate creates the in-progress check and saves an armed run (a placeholder nonce, head SHA, 5-minute deadline) on the PR's state. Once GitHub accepts the dispatch, the gate replaces it with the run ID, the dispatched nonce, and the runner's deadline. A dispatch error therefore still leaves a check and a run for the deadline sweep to close.
3. The workflow installs Claude Code, checks out the head commit into a subdirectory, and runs Claude Code, told to review the candidate docs, then uploads a result artifact (always, even on failure) and a separate transcript artifact.
4. A `workflow_run` completed event arrives. The run ID maps to its PR.
5. The runner downloads the artifact. The gate accepts it only if the run is the one dispatched for the PR's current head and the artifact's head SHA and nonce match.
6. The server first validates the complete structured output against the static result schema: missing or wrongly typed fields, extra fields, and invalid document paths invalidate the whole result. Every proposed path is also checked for a clean, safe `.md` or `.mdx` path under `docs/`, and more than 20 proposals invalidates the whole batch before any partial acceptance. Collection does not enforce the workflow's per-PR anchor schema or new-doc conditional as schema requirements; those are checked per proposal by finalize. A failed read of the base docs at collect ends neutral like an unreadable result, and a failed read when a run starts ends neutral "Reading the repository failed.", the cause the server runner also reports for a failed clone. The server then runs the proposals through the same finalize step as the server runner (see [Server runner](server-runner.md)): section names are normalized and the rules checked, including that each anchor is a numbered line inside its file's hunks and that a result carries at most 20 proposals. A new-doc proposal without a non-empty `title` and `summary`, with a non-relative link to another doc of this repo (a `/docs/...` path or a GitHub URL to its docs), or whose `covers` match none of the uncovered files is rejected; the server recomputes that set at collect, at the merge base the run started at (stored with the run), because the artifact is not a second source of truth and head would diverge when the PR adds a covering doc. A run started before the base was stored has its new-doc proposals rejected, since their `covers` cannot be checked. A new doc's path must be free at head (nothing there, and no file, symlink, or submodule above it), and a section edit needs its doc at head (fetched once per doc at the head SHA) with the heading present exactly once. The same step fills each section proposal's original text and line range, so comments show the old text and can become suggestions; a doc with broken frontmatter still yields its section text. Unlike the server runner, which sends problems back to the model and accepts no invalid submission, collection drops proposals with finalize problems and returns the valid proposals in their original order, without asking the model again. A mixed result concludes `action_required` and posts comments only for the survivors. If every proposal is invalid, the whole result fails: the check ends neutral "Analysis failed", rather than reporting no impact. A schema failure, unsafe document path, or oversized batch also fails the whole result even when another proposal is valid. Transient failures reading head files or listing changed files are retried; they do not turn into dropped proposals. The check and summary include one bounded, sanitized line with the dropped proposal count and reasons, never the rejected content. This metadata is saved with PR state before posting comments, survives posting retries, restarts, and Apply or Skip redraws, and is replaced or cleared by the next completed analysis. The no-impact reason is stored as one capped line. Otherwise the same transition as the server runner concludes the check: success ("No doc impact" with a reason) or action_required with the proposals.

## Invariants

- **Match by run ID, never SHA.** Runs report the default branch's SHA, not the PR head, so the head SHA cannot identify a run.
- **One ending path.** Server-runner results, artifact results, failed runs, and missed deadlines all conclude the check through the same transition.
- **Never stuck in progress.** A failed, cancelled, or timed-out run, an invalid result, a result the server cannot read, a dispatch error, a failed or oversized read of the docs (before dispatch the server reads every `.md` under `docs/` at the merge base through the Git Data API, only that subtree with blobs cached by SHA; more than 500 docs or a failed read ends neutral "Analysis failed" without dispatching), or no result before the deadline ends neutral with a fixed one-line cause naming which (5 minutes for a review run, which tolerates a slow Actions runner past the 3-minute target, and 10 minutes for a scaffold run, which is not on a PR's path; the sweep runs every 10 seconds); the artifact's own error text stays in the server log, since it can carry model output. A periodic sweep closes any armed run past its deadline neutral and retries with backoff if GitHub rejects the write (see [Job queue](job-queue.md)). The concluded state is saved before comments are posted; if posting still fails after retries the run is re-armed and the sweep ends the check neutral with a Re-run box, so a check never claims proposals that were never posted.
- **Size limits first.** A PR over the limits (see [Server runner](server-runner.md)) ends neutral "PR too large to analyze" before any review dispatch. More than 10 candidate docs also ends neutral, as in the server runner, without dispatch.
- **A new analysis supersedes.** Any new analysis of a pull request that awaits a run (a push, or a repeat event for the same head) first concludes the old in-progress check neutral ("Superseded by <short sha>", or "Superseded by a re-run" when the head is unchanged), then clears the pending run and dispatches the new head; the old run's late result matches nothing and is ignored. Events for any other run, a stale nonce, or a different head SHA change nothing.
- **Base candidates.** Matching `covers` at head would let a PR empty or narrow them to opt itself out, so the candidates come from the merge base. The run's "No doc impact" is trusted, the same trust the server runner gives triage. The workflow is still dispatched when no doc covers a changed file but some uncovered file may need a new doc. A candidate the PR deletes concludes the check with a restore proposal and no dispatch (see [Server runner](server-runner.md)).
- **Generated prompt.** `action/prompt.md` is generated by `make generate` from `internal/review/instructions`, the rules the server runner's prompts also use, so a rule change reaches both runners; edit the rules, not the file.
- **New-doc decision.** That a new doc is needed is enforced only by the prompt here (the server runner enforces it in code); the `covers` rule is enforced by the server for both runners.
- **Read-only agent.** Claude Code gets Read, Grep, and Glob over the checked-out head commit and the diff file, nothing else is pre-approved; other tools are blocked, not merely unapproved, because pre-approval alone doesn't stop the model from trying them.
- **Anchors the agent validates itself.** `action/run-claude.sh` gives Claude Code `pr.numbered.diff`, the diff with the head-side line number printed on every context and added line (`action/numbered-diff.awk`, byte-identical in its hunks to `review.NumberedPatch`), and builds a per-PR schema for `--json-schema` from `result.schema.json`: each proposal's anchor must name a changed file and a line inside one of that file's head-side hunk ranges (`anchor-schema.jq`; the ranges are the server's `files` from the dispatched input, so the commentable lines are exactly what the server validates, and with old input lacking them they come from the hunks of the action's own `pr.diff`;  one compact entry per file, hunks from `diff-hunks.awk` written to a file, never passed as an argument; deleted files and hunks without head lines are skipped, and paths git still quotes are decoded; `pr.diff` is the head diffed against the dispatched merge base (`base_sha...HEAD`, computed in the "Run Claude" script so the eval runs it; old input without `base_sha` falls back to the default branch) and is written with `core.quotePath=false` so non-ASCII paths match GitHub's). The schema also carries `review.Proposal.Validate`'s new-doc rule (`new-doc-schema.jq`: `index_entry` is set iff `section` is empty), applied even when the anchor ranges fall back. Claude Code validates its structured output against that schema and re-prompts on a mismatch, so the model corrects an anchor on an unchanged file or line, or a new doc without its index entry, itself. A diff with no hunks, or a schema over 100 KiB, drops the anchor ranges and keeps only the new-doc rule on top of the static schema. An anchor outside the server's hunks for the PR is still invalid and its proposal is dropped at collection; if no valid proposal remains the result fails (`InvalidResultError`); the gate's file-level fallback is defensive only (see [Proposal output](proposal-output.md)).
- **The schema and the server agree on hunks.** The per-PR schema's ranges are the server's own, so a PR targeting a non-default branch and a file whose patch GitHub omits (no ranges, so no anchor can land on it) behave the same on both sides. They can disagree only on old input without `files`, where the ranges come from the action's own diff; Claude Code then passes its schema but the server may drop proposals whose anchors fail validation.
- **Inspectable runs.** Claude Code runs with `--output-format stream-json --verbose`; the NDJSON stream is the `pollux-agent-transcript` artifact (14 days, separate from `pollux-agent-result`, which the server downloads by name). `claude` in the result is the stream's final `result` line, the same object `--output-format json` printed. The job log has an "Agent trace" group with one line per Read, Grep, or Glob call and a closing line of turns, duration, cost, and tokens. File contents never reach it, and workflow commands are disabled around it because tool inputs come from the PR. The transcript holds file contents the agent read, so it is as sensitive as the repo.
- **Usage is reported.** The result carries the run's token totals (input, output, cache read, cache write) and `total_cost_usd` from the `claude` object, and the `costBasis` the models share (empty if they differ or none is given). Under an OAuth token the cost is a list-price estimate, not spend, and `costBasis: "list"` is the only marker. Every field is optional: a run without a usage block reports no usage, and one without a cost reports tokens only. The artifact is untrusted, so usage is decoded best-effort and never fails a result: a malformed field is dropped, negative values and values above 1e12 tokens or 1e6 USD count as not reported, and the model name and `costBasis` are capped at 200 and 32 bytes.
- **Auth failures are errors.** A rejected credential still reports a successful subtype, so the action treats Claude's error flag as failure and the check ends neutral with a fixed one-line cause naming which; the artifact's own error text stays in the server log, since it can carry model output.
- **Isolated agent.** Claude Code is installed before the checkout, from a directory with no PR content, and runs in an empty directory outside the checkout. Project settings, hooks, `CLAUDE.md`, and MCP servers from the PR are never loaded (`--setting-sources user`, `--strict-mcp-config`), and reads outside the checkout and the diff are denied, so PR content cannot run code with the credential or read it from the runner.
- **Dispatch inputs change together.** An input is added in Dispatch (server), `action/action.yml`, `action/pollux-agent.yml`, and the setup guide's YAML at once. GitHub rejects an undeclared input, so a repo on an older workflow copy fails every review until it re-copies the workflow. For that reason the uncovered list rides inside the existing `docs` input instead of a new one. The "Run Claude" step's logic lives in `action/run-claude.sh` so the [eval](../guides/eval.md) can run it unchanged; the step's `env:` in `action/action.yml` and the eval's local stand-in must pass the same variables. The script runs under `set -u`, so a variable missing on either side fails the run, and `make eval-check` (also in CI) runs the script against a stub `claude` to catch a mismatch. Changing the shape of an existing input is the same kind of change: the action keeps accepting the old shape, and because installs use `action@main`, the action change reaches main before a server sending the new shape deploys. A workflow pinned to an older action version fails every review until it updates.
