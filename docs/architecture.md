# Architecture

pollux is a GitHub App. GitHub sends pull request events to the backend; the backend reads the diff, finds the docs that cover the changed files, asks an LLM whether they need to change, and reports the result as a check run that can block the merge.

## Parts

- **Backend** (`backend/`, Go): receives GitHub webhooks, talks to the GitHub and LLM APIs, owns the check run. `POST /webhook` rate-limits by client IP (from `X-Forwarded-For`, walked right to left past loopback and private-IPv4 proxies such as Funnel or Docker's bridge; see [Deploy](guides/deploy.md)) and globally before reading the body, then verifies GitHub's signature. `/auth/*` has its own per-IP and global limiter (see [Sign in with GitHub](features/sign-in.md)). For a `pull_request` event (opened, synchronize, reopened), a `workflow_run` completed event for a run the backend dispatched, or a human `issue_comment` or `pull_request_review_comment` event, it stores the delivery and a durable job in one SQLite transaction, deduplicated by GitHub's delivery ID; other events are acknowledged without being stored. A periodic sweep enqueues a deadline job for each awaited Actions run past its deadline, and the worker deletes finished jobs and their deliveries after 7 days (see [Job queue](features/job-queue.md)). Accepted deliveries return 202. A worker processes jobs off that queue: it runs at most one job per key at a time (a PR, or a repo's scaffold) but keys in parallel, a newer push supersedes the older job for the same PR, cancelling it if it is already running, and jobs left unfinished by a restart resume afterward. The `pull_request` job picks an analysis runner for the repo and reports its result as the `pollux-agent` check run on the PR head commit.
- **Frontend** (phase 2, TypeScript + shadcn/ui): org and repo settings, configurable docs structures.
- **Doc targets**: phase 1 writes to the repo's own `docs/` folder. Notion comes in phase 3.

Inside the backend, `internal/gate` is the domain and imports only `internal/review`, the contracts shared with the analysis runners. It declares the GitHub, CommentGitHub, ScaffoldGitHub, ScaffoldQueue, and Store interfaces it needs; `internal/github` implements the first three, `internal/httpapi` implements ScaffoldQueue by enqueueing repo-keyed scaffold jobs, and `internal/gate/sqlite` implements Store. `internal/httpapi` turns webhooks into jobs on `internal/jobqueue`, the durable queue, and decodes them back into `gate.Service` calls when the worker runs them (PR jobs per PR, scaffold jobs per repo); `internal/gate/sqlite` implements both `gate`'s and `jobqueue`'s storage interfaces on one SQLite database. `internal/gate/sqlite` is an adapter, not part of the domain. Sign in with GitHub follows the same shape (see [Sign in](features/sign-in.md)): `internal/auth` is its domain, stdlib only, declaring `Store` and `GitHubUser`; `internal/github` implements `GitHubUser` with a user client; `internal/gate/sqlite` implements `auth.Store`; `internal/httpapi` mounts the `/auth/*` and `/api/*` routes when `cmd/server` passes a configured service. Alongside each PR's state it stores an append-only history of analyses and Apply/Skip events, written in the same transaction (see [Analysis history](features/analysis-history.md)). Only `cmd/server` wires concrete types together. The queue's guarantees are in [Job queue](features/job-queue.md). A runner that needs GitHub credentials outside the API client (the server runner's `git` clone) gets `github.Client.InstallationToken` from `cmd/server` as a function, not the client, so no runner imports `internal/github`; the token is narrowed to one repo with `contents: read`. The gate, review, docs, llm/agent, and runner import rules, and that only `internal/config` reads the environment (one `nolint`'d exception: the server runner's `git` subprocess env), are enforced by `depguard` and `forbidigo` in `backend/.golangci.yml`, so `make lint` fails on a violation.

Runner selection: a repo that has the pollux-agent Actions workflow on its default branch runs analysis through the Actions runner; otherwise, if the server has `LLM_PROVIDER` configured, it runs through the server runner; otherwise the PR gets a neutral check titled "No analysis runner configured" linking the setup guide (or "No docs/ folder" with the same link when the head has no `docs/`). The server runner is described in [Server runner](features/server-runner.md). It is built from `internal/review/pipeline`, which implements `review.Runner` and `review.Scaffolder` over a backend and a judge and imports neither `internal/llm` nor `internal/agent`, and `internal/review/llmrunner`, the backend (clone, agent loop, triage-model judge); `cmd/server` composes them. A repo with the workflow never falls back to the server runner. The Actions runner makes no LLM call on the server: the gate dispatches the workflow, the repo's own Actions run Claude Code with the repo's credential, and the result comes back as an artifact. The same selection picks the writer for the docs scaffold, a repo-keyed job separate from PR jobs (see [Docs scaffold](features/scaffold.md)). See [Actions runner](features/actions-runner.md) and the [setup guide](guides/actions-runner.md).

Analysis contract: `internal/review` defines what a runner is asked to review and the proposals it returns, and imports nothing else from this module, so both the gate and the runners can depend on it. `action/proposal.schema.json`, `action/result.schema.json` (the no-impact-or-proposals result Claude Code must emit in the Actions runner), and `action/scaffold.schema.json` are generated from the `internal/review` types by `make generate` and checked in; never edit them by hand, a test fails when any drifts. The Actions runner's prompts, `action/prompt.md` and `action/scaffold.md`, are likewise generated by `make generate`, from the rules in `internal/review/instructions`; the server runner's prompts embed the same rules, so changing a rule there changes both runners, and a test checks each rule appears verbatim in both. The Actions runner derives a per-PR copy of `result.schema.json` at run time (`action/new-doc-schema.jq` adds the new-doc `index_entry` rule, `action/anchor-schema.jq` narrows `anchor` to the PR's hunks), so moving or renaming `section`, `index_entry`, or `anchor` in the contract must update those jq paths; `TestActionNumbersDiffAndRestrictsAnchors` fails if it drifts. The schema checks shape and the `docs/` prefix; proposal validation in `internal/review` is the full check (`doc_path` a `.md` or `.mdx` file under `docs/`, no control characters or backticks in paths, single-line section and index entry, anchor on a file the PR changes and does not delete, on a line inside one of that file's hunks (the error lists the commentable ranges), one-line reason, index entry exactly when the proposal creates a new doc), and every runner's output must pass it before the gate acts on it. Both runners also check a new doc against the base docs: it must be a parseable `.md` doc within the size cap with a non-empty title and summary, a covers key, and relative links to other docs of the repo (no `/docs/...` paths or GitHub URLs to this repo's docs; links in code are ignored), and its `covers` must match at least one changed file no base doc covers. That check lives beside the candidate selection because the contract package may not depend on the docs parser. Apply validates the stored proposals again before committing. Scaffold output is held to the same convention (title, summary, covers key, relative links), and its index must link both siblings; the rule covers a proposal's index entry as well as the doc.

Docs model: `internal/docs` reads the `docs/` tree of a checkout into docs (frontmatter and sections) and matches changed files to docs by their `covers` globs, relative to the repo root with `**` crossing folders. It takes a file system, never calls GitHub, and imports no other internal package. A doc with no frontmatter block, unparsable YAML, wrong field types, or a `covers` glob that is invalid, not repo-relative, or too costly to match is reported and skipped, never fatal, because phase 1 must work on existing docs it does not restructure; a missing `title` or `summary` is not an error. PR content is untrusted: the walk reads only regular files under 1 MiB, never symlinks. A section runs from its heading to the next heading of the same or higher level, so replacing a `##` section replaces its `###` subsections too; this is the unit a proposal replaces. Only `#` headings start sections; setext underlines and `#` lines inside code fences are body text. Duplicate headings are allowed.

## Flow (phase 1 target)

1. A PR is opened or updated; GitHub sends `pull_request` to the backend.
2. The backend lists the PR's changed files; the analysis runner maps them to docs through each doc's `covers` globs at the PR's merge base (the base-branch commit its diff starts from), so a PR cannot opt itself out by editing `covers`; doc text is read at head (see [0002](decisions/0002-docs-structure.md)).
3. The LLM compares the diff with those docs and returns "no impact" or proposed edits. For changed files no doc covers, it decides whether a new doc is needed.
3a. If the PR head has no `docs/` folder, the check ends neutral as "No docs/ folder" and nothing is analyzed; the repo gets a one-time scaffold PR instead (see [Docs scaffold](features/scaffold.md)).
4. The backend sets the `pollux-agent` check: `success` for no impact, `action_required` otherwise, and posts one review comment per proposal plus a summary comment (see [Proposal output](features/proposal-output.md)).
4a. If analysis fails or the PR is over the size limits, the check ends neutral with a fixed cause and the summary offers a "Re-run analysis" checkbox, handled like the other summary checkboxes (see [Apply and Skip](features/apply-skip.md)); GitHub's Re-run on the check does the same. The check never stays pending.
5. A developer applies, edits, or waives the proposal; the check turns green and the PR can merge. Apply and Skip arrive as comment events, run as `comment` jobs, and commit to the PR branch (see [Apply and Skip](features/apply-skip.md)).

## Phases

1. In-repo `docs/`, hard-coded default structure, merge check. See [0001](decisions/0001-in-repo-docs-first.md).
2. Frontend; structure becomes configurable.
3. One-way sync from repo docs to Notion.
4. Custom structures defined by users with their own prompt.
